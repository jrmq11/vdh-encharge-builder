**Standing rules.**
- Every Encharge call goes through `guard.js`. `VDHSit` never calls fetch.
- Permissions start empty. Never load `tests/specs/permissions.json` live: its grants are for the offline tests (since v1.02 the compiler refuses it, and the page refuses any plan compiled with it). Joe's words go in the session's own `permissions.json`, each entry with the date; since v1.02 the page sets a run's permissions itself, from the plan it loaded by its hash, so nobody types them in.
- Claude never switches a flow on.
- People never leave the page: counts, and matches against hashed emails, only.
- FlowMattic: reads only.
- Before each of Joe's steps, brief him: what and why, what should happen, pass or fail, what to send back. Links he must click go in the chat, opened once. His steps happen in his own browser, never in Claude's tab.
- **Show Joe each plan before it runs** (objects, number of calls, permissions used, warnings), and run it on his go. One go may cover several runs he approves together.
- **The builder's code does not change during a sitting.**

**A check passes only on evidence, derived at check time.**
- An expected value is worked out from the source at the moment of the check, through the same path the check reads (a file's hash as the page will hold it, the master as it stands, the account's tags as read today). It is never typed in from an earlier run.
- **An expected value comes from an object in the same state.** v0.4 took "listener ids on every email link" from the live flow 310308, which is on, and expected them on a draft never switched on; R1's in-page check failed on the builder's correct draft (2026-09-26). When the only example is in another state, run a control that changes only that state (Joe switched R1 on, then off).
- Every "nothing happened" check carries a control that shows the method can see something happen.
- **A cause is proven only by Encharge's own words, or by A-B-A:** the original fails, the change passes, the original fails again. A fallback that works proves only that the fallback works (the review of B1's plan, 2026-09-25: had the full name failed and a plain name then passed, that alone would not show that any character, or which one, was the cause).
- A reader read counts only if the validator passes it and it is stamped after the action it checks (`--after`, the tagged output of `live/readers_check.py now`, Paris store time).
- A count or a list counts only if its paging is proven: a list the page cannot read whole is a failure, never a short list.
- Joe's eyes are recorded as a separate piece of evidence, never in place of a script's check.

After any run that edited an existing segment (the objects plan's People IN FLOW rows, the switch-over's Abandoners edit), record each edit with `python3 -B live/pagecmd.py ledger edited ledger.json segment:<id> --change "<rows added and removed>" --joe "<Joe's words>" --run <name> --snapshot <the snapshot file>`, which keeps the snapshot's rows in the ledger, for Joe to restore by hand should he need to. Only what that run made goes in, never the ledger's own, with its new tags and fields by name. A run name is used once; a rerun needs a new name. A rebuild's old entry came off the key before the compile (the compiler refuses a flow, email or segment key the ledger holds live): a superseded draft was marked `failed`, and now moves, with its state, to `<key>-old-<date>`, as the new ID takes the key; a flow Joe has switched on was moved, state and all, to `<key>-live-<date>`, and is never marked `failed` while it is on. A tag or field made anew replaces its `deleted` entry, which it keeps under `replaced` (`SKILL.md`, The ledger). `ids()` answers flat keys (`flow:zz_r1_bounce`, `segment:…`, `email:…`, `tag:…`, `field:…`, and each step and position); the tool nests them by kind (`SKILL.md`, The ledger). A tag or field it names that is in `tags.json` or `fields.json` (the session's first reads) was there before the run: the tool lists it under `leftOut`, and writes it as not the builder's (no state, off the delete list), so that the page's record of the run, which names it, clears. `--tags` and `--fields` are always the first reads of the session that ran it: a later session's read holds what the run made, and the tool refuses one saved after the record's `verifiedAt`.

**After any failed or interrupted run, before anything else:**
1. Report `failedAt`, `do`, `step`, `error`, `encharge` (Encharge's own status and error text) and `mayExist` exactly. `mayExist` names each object whose create call went out without its own ID coming back (no answer, an error, or an answer without the ID): Encharge may have made it. A call that got no answer at all is recorded as sent (`byStatus` counts it as `no answer`).
2. `VDHGuard.setPermissions([])`. Then `VDHSit.journal()` and `VDHSit.created()`, and `JSON.stringify(VDHSit.reconcileDue())`, saved verbatim as `marker-<name>.json` (it records what the run made; a reconcile that resolves clears it).
3. **Reconcile:** send the output of `python3 -B live/pagecmd.py reconcile ledger.json <the failed plan> --tags tags.json --fields fields.json`, as written (its hash is checked in the page, 2.3; v1.07). The page refuses any new run, of any plan, until a reconcile has read Encharge's four lists whole **and found them agreeing with the ledger** (v1.01): the marker lives in the page's local storage, so a reload or a reinstall keeps it (`VDHSit.reconcileDue()` shows it: `running` for a run cut short, `failed` for one that failed after a write, `unverified` for one whose verify failed). A run that failed having only read, or before its first call, leaves none. Reconcile lists every flow, segment, tag and field named ZZ (`zz_`), or with a name from the plans given or from the marked run's plan, each with `known` (to the ledger) and `matchedBy` (`zz` or `name`); what the ledger knows that Encharge's lists lack (`…MissingKnown`); and what the ledger marks deleted that the lists still hold (`…StillThere`). It also requires every object the marked run made, as its marker recorded each create Encharge answered (`madeByRun`; flows and segments by ID, tags and fields by name; missing ones in `…MadeMissing`), and every tag and field of the session's first reads (`…MissingAtStart`, with `--tags` and `--fields`): a list cut short cannot then hide what a failed run made (gap A19). An object the run may have made (the create that was out when it stopped, or got no answer, a timeout or a server error; or one answered without its ID) is settled when a list shows it: a tag or a field by its name, a flow by a new flow of its name (not one the ledger knows or the marker names: a rebuild's old draft keeps its name). Otherwise it is in doubt (`…InDoubt`), and a segment or an email always is (`segmentsInDoubt`, `emailsInDoubt`): the segment list is not paged (gap A19), and emails have no list call. Each object the marked run made, as its marker recorded Encharge's answer, is marked `madeByRun` in the lists, and its emails are in `madeByRun.emails`, by ID. It answers `ok` (`resolved`) only when all these lists are empty and every list was read whole; otherwise `why` says what to settle, and the marker stays. Objects the ledger does not know are listed, for the ledger, and do not block.
   - **A known object missing** is one Joe deleted by hand, or a list that came back short (gap A19), which could hide what the run made too. Ask Joe. If he deleted it, `python3 -B live/pagecmd.py ledger delete ledger.json <kinds> <key> --joe "<his words>"`, and the reconcile call is written again from the ledger: `pagecmd.py` then expects it gone (`deleted`), and `refs` and the compiler never use it again.
   - **An object marked `verifiedRun`** belongs to a verified run the ledger does not hold yet (the answer's `unledgered` names the run). It goes into the ledger with that run (2.2, or step 8), never on a delete list; the ZZ rule below does not apply to it.
   - An unknown ZZ object marked neither `verifiedRun` nor `madeByRun` goes into the ledger as `failed`, for Joe to delete by hand, once he has said so: `python3 -B live/pagecmd.py ledger put ledger.json <kinds> <key> --entry '{"id": <ID>, "state": "failed", "name": "<its name>", "note": "listed by reconcile, <date>"}' --joe "<his words>"` (a tag or field by name, without `id`).
   - **What the run made** (`madeByRun` on a listed object, and each email in `madeByRun.emails`): the run's own, as its marker recorded Encharge's answer (a tag or field of the session's first read is never marked so: it was there before). Each goes into the ledger as `failed`, since the run never verified: `python3 -B live/pagecmd.py ledger made-ids <the failed plan> marker-<name>.json --run <name> --tags tags.json --fields fields.json --out made-<name>.json` keys what the marker recorded by the plan's names, leaving out a tag or field of the session's first reads (what it cannot key, a create answered without its ID or with a name the plan does not give, it lists on stderr, for Joe to look for), then, unless it wrote `{}` (nothing with an ID: skip this), `python3 -B live/pagecmd.py ledger add ledger.json made-<name>.json --run <name> --plan <the failed plan> --state failed --tags tags.json --fields fields.json`. A tag or field the run made that Joe keeps rather than deletes: `ledger keep ledger.json tags|fields <name> --joe "<his words>"`; the compiler counts every tag and field the ledger holds live as the account's, so the rebuild never makes it again. `made-ids`'s answer carries when the run started, and `add` refuses a first read saved after that. After a reload, which loses `VDHSit.ids()`, this is the record.
   - An unknown object matched by name only, and not `madeByRun`, may be one that was there before the run (a tag or field says `atStart: true` if it was in the session's first read): Joe checks it in Encharge before anything is decided; a live object is never put on a delete list on reconcile's word.
   - **The ledger's emails, read by ID (v1.11, P4):** each email the ledger holds is read by its ID. One it holds live that is archived or gone is a known object missing (`emailsMissingKnown`, above); one it marks deleted that is still there unarchived keeps the marker (`emailsStillThere`): Joe deletes it by hand; one whose read failed another way (`emailsUnread`) leaves the lists unread: reconcile again.
   - **Emails have no list call:** `emailsToFind` names each email to look for: the one in doubt (`emailsInDoubt`: its create was out when the run stopped, or got no answer, a timeout or a server error) and those a failed run's summary named (`mayExist`). Joe looks for each by name among Encharge's emails; if it is there and he confirms it was not there before the run, it goes into the ledger as `failed` by its ID, with `ledger put … --joe` (as above).
   - **An object in doubt** (`…InDoubt`, `emailsInDoubt`) keeps the marker, however the lists read: only Joe can say whether Encharge made it. He looks for it by name, the ledger records what he finds (`ledger put … --joe`, `failed`, by its ID, if it is there and was not there before the run), and then a waive with his words clears the marker.
   - Reconcile holds the builder's lock while it reads, and refuses while another copy of the builder holds it (a run still going in another tab, or in an install replaced mid-run without a reload). It also answers `ok: false`, "reconcile again in N s", for two minutes after the page stopped waiting for a call Encharge may still be acting on, so the lists show what that call did: a write (not a read) that got no answer, a timeout or a server error (408, or any 5xx: a gateway's 502 to 504, Cloudflare's 520 to 524, Encharge's own 500), counted from the failure; a run cut short, counted from the first reconcile after the reload.
   - A `built` run this page still holds is settled by its verify, not by reconcile, which refuses it. One the page lost (a reload) is settled by reconcile, which says it was never verified (`unverifiedRun`): mark what it made failed in the ledger (nothing stands in for its verify), and rebuild what is needed.
   - If a list cannot be read whole, or the lists and the ledger disagree in a way only Joe can settle, the marker stays: find out why with Joe. Only once this page's reconcile of the marker has come back unresolved and Joe has checked Encharge by hand, `await VDHSit.waiveReconcile('<run>', '<Joe's words>')` clears it; its answer (his words, the marker's names, what the run made, and the emails to find) goes in the results.
