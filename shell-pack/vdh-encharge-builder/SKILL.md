## Rules

**Owner calls (Joe, 2026-09-23):** *"every flow off yes"* · *"api - not unless express permission given"* · *"express permission must be given but you could edit those tags"*.

1. **Every flow arrives off; Joe switches it on.** Encharge creates flows off, and nothing on the guard's list can switch one on. Claude never switches a flow on, and never changes a live flow's settings: the settings call carries the on/off status.
2. **No edit to an existing object** without Joe's express permission. The builder is create-only for flows.
3. **Steps that add or remove `product_*`, `refunded_*` or `abandoned_active` need Joe's express permission**; with it, they can be built.
4. **Express permission comes only from Joe's own words in the chat, naming the object.** Record it in the session's own `permissions.json` as `{"object": "kind:key", "id": <Encharge id if any>, "action": "…", "joeSaid": "<his words>", "date": "YYYY-MM-DD"}`, with the action from the table below. Since v1.02 the compiler refuses an entry without his words or the date, one whose words are a note in brackets, such as the offline suites' "(offline test only)", or a test's words ("offline test", "dry run", "rehearsal", "not Joe", found in the words' letters and digits alone, so however spaced, cased, hyphenated, glued or plural), and a date no calendar has, before 2020 or after tomorrow; invisible and control characters do not count as words. The page and the ledger tool judge words the same way. If Joe's own words happen to hold one of these ("no need for a dry run"), ask him to give the permission again in other words; never shorten or edit what he wrote. The same rule covers: editing a live segment (People IN FLOW, Abandoners), End Flow naming a flow outside the build, `includePeople: "currentAndFuture"`, Update field on one of the twelve protected fields (the ten the FlowMattic routers write, and `LastLoginDate` and `LoginCount`, which WP Fusion writes; the code calls all twelve router fields), Archive person and Send webhook.
5. **Every call goes through `guard.js`.** Never call `fetch` directly, and never bypass or edit the guard in a session. Never read `GET /v1/accounts` (its answer holds the API key). Never load `tests/specs/permissions.json` live: its grants are for the offline tests (since v1.02 the compiler refuses any permission file in the package's `tests` folder, unless `--offline-permissions`, whose plans neither `pagecmd.py` nor the page will load).
6. **Check before saving, read after.** Encharge saves segment rows without checking them: the compiler checks every row, the runner reads each segment's preview straight after saving and stops on a 500, and every run ends with a read-back that `verify.js` checks.
7. **A failed flow is rebuilt whole.** There is no resume and no delete by API. Reconcile first (the page refuses any run until it has), mark the draft `failed` in the ledger, and Joe deletes it by hand.
8. **Capture hygiene.** A HAR file holds the account API key: don't reload while recording, delete the HAR after upload. Evidence files leave out `GET /v1/accounts`, contact lists and autosave bodies.
9. **People never leave the page:** counts and hashes only. Reader buffers that hold contact data stay in the workspace.
10. **FlowMattic: reads only.** Before any write, name the tool, the target and the change, and ask Joe about a backup.
11. **The builder's code does not change during a session in the page.** A fault found there is recorded and fixed in the next version. Show Joe each plan before it runs.
12. **Never navigate or reload Claude's tab after the install.** For a second page, open a new tab; Joe's own steps happen in his own browser. The exceptions, each on Joe's go: a recovery drill once a run is verified and its IDs are in the ledger (never between a run and its verify: a reload loses the run's record), and a run that hangs.
13. **Nothing that depends on an open gap goes live before the gap closes.** The one planned exception is Checkout Abandon's product check at the switch-over (`references/gaps.md`, A12 and D1).
14. **A check passes only on evidence derived at check time**, through the same path the check reads, from an object in the same state; every "nothing happened" check carries a control; a cause is proven only by Encharge's own words or an A-B-A repeat (`live/RUNBOOK.md`, top).

**Working with Joe.** Brief him fully before each of his steps: what and why, what should happen, pass or fail, what to send back. Name the system with every object ("Encharge flow …", flows by display name, ID in brackets). Give each link he must open in the chat, to open once. Add a diagram when explaining a process. Before asking for his words on a protected tag, show him everywhere it is used today, in Encharge's flows and segments and in the FlowMattic routers (reads only): he asked for exactly that at sitting 2b.

**Permission entries.** For a segment or a flow, give both the key and the Encharge ID: the compiler refuses an entry without the ID, or whose key and ID disagree with the ledger, and the guard matches the ID. Each entry names one action from the table; there is no wildcard. Permissions start empty in every session, and the guard in the page holds only the entries a run uses: since v1.02 the page sets them itself, as the run starts, from the plan it loaded by its hash (the entries its report lists as used, each with Joe's words and date), and empties them as soon as it ends. Nobody types them into the page. A protected tag takes one entry, `tag:<name>` / `use`, whatever the number of steps that use it: the compiler's report then lists it once per step (8 for Checkout Abandon at sitting 2b), while `load` answers the distinct entries (1), the same permission (`references/gaps.md`, P13).

| What needs permission | `object` | `action` |
|---|---|---|
| Add or Remove tag on `product_*`, `refunded_*` or `abandoned_active` | `tag:<name>` | `use` |
| Creating such a tag | `tag:<name>` | `create` |
| Editing an existing segment | `segment:<key>`, with `id` | `patch` |
| End Flow naming a flow outside the build | `flow:<key>`, with `id` | `end` |
| Update field on a protected field (the FlowMattic routers' ten, WP Fusion's `LastLoginDate` and `LoginCount`) | `field:<name>` | `set` |
| Entered segment that enrolls people already in it | `includePeople:currentAndFuture` | `use` |
| Archive person; Send webhook | `op:/archive`; `op:/send-webhook` | `use` |

## The ledger

**Where it lives.** The ledger's home is the Project doc `encharge-api/Encharge-Sitting-Ledger-2026-09-25.json` (D3: Joe's laptop folder holds working copies only): save it as `ledger.json` at the start of a session, and write it back to the Project after every run, to that same full path. Every builder doc in the Project lives in `encharge-api/` (Joe, 2026-09-28): a doc written by its bare file name would land in `claude/` instead, so always give the full path. The workspace does not carry over between sessions: a new chat writes `ledger.json` from the Project read, and `ledger check`, then the start reconcile against Encharge's lists, prove it before any run; `project_write` with `local_path` writes it back without re-typing it (sitting 2a).

**Written by a tool (v1.02).** `python3 -B live/pagecmd.py ledger <command>` writes it, never a hand edit, and checks the whole ledger before every write (one ID per key, whole-number IDs, the builder's states, the known kinds); it writes a new file beside it and puts it in place whole. Each command answers in JSON what it wrote, and refuses an option it does not take and a `--date` that is not a calendar day. `<kinds>` is `flows`, `segments`, `emails`, `tags` or `fields` (`flow`, `segment` … also do):
- `add` records a run: from what `VDHSit.ids` answered, or after a reload what `VDHSit.unledgered()` answered, or for a run that never verified what `made-ids` wrote; with the plan it ran, for names and provenance. Answers `{"added": {…}, "moved": […]}`, and `leftOut` for a tag or field that was there before the run.
- `made-ids <plan> <marker.json> --run <name> --tags tags.json --fields fields.json`: the IDs a run that never verified made, keyed by the plan's names, from its marker (what `VDHSit.reconcileDue()` answered before the reconcile, or the waive's answer); a tag or field of the session's first reads was there before, and is left out; what it cannot key, it lists for Joe; `{}` means nothing to add. Its answer carries when the run started (`_marker`), and `add` refuses a first read saved after that.
- `supersede <kinds> <key> --joe "…"`: a verified draft (`built-off`) Joe agrees is superseded becomes `failed`, with his words; nothing else can be superseded.
- `live-move <key>`: a flow he has switched on (`handed-over`) moves off its key, before its rebuild; `switched-off <key>-live-<date> --joe "…"` marks it `failed` once he has switched it off, after switching its rebuild on.
- `handed-over <key> [--listeners ok]`: he switched the verified draft on.
- `delete <kinds> <key> --joe "…"`: he deleted it by hand.
- `keep tags|fields <name> --joe "…"`: a tag or field a failed run made that Joe keeps rather than deletes becomes `built-off`, with his words. The compiler counts every tag and field the ledger holds live as the account's, so a build never makes it again.
- `put <kinds> <key> --entry '<JSON>' [--joe "…"]`: one entry no run wrote (an email Joe made by hand; an unknown ZZ object reconcile listed, by its ID, `"state": "failed"`, which needs his words), never over an entry the ledger holds. No command ever gives a live object the builder did not make (Encharge flow Abandoned Cart Email Sending Sequence, the seeded segments, Encharge email Tester 1, and since v1.05 Encharge email VDH Master · Letter, 488125) a state but `deleted`: `ledger check` refuses it, so it can never reach the delete list.
- `edited <kind>:<id> --change "…" --joe "…" [--run <name>] [--snapshot <file>]`: an edit to an object the builder did not make (the objects plan's rows on People IN FLOW, the switch-over's edit to Abandoners), under the ledger's `edited`, with the snapshot's rows kept in the entry (the workspace does not carry over). Also any hand change to the master, Encharge email VDH Master · Letter (`edited email:488125`, then `#2`, `#3` …, the version named in `--change`): the ledger has no note command, `edited` is the one that fits, and `put` refuses a key the ledger already holds. Such a note leaves the `refs` and `reconcile` calls byte for byte the same (sitting 2a: three notes, both hashes unchanged).
- `check`: answers `ok`, or each problem.

The rules below are what the tools do.

**What it holds,** by kind, in build order: `{"fields": {"<name>": {…}}, "tags": {"<name>": {…}}, "emails": {"<key>": {"id": …}}, "segments": {"<key>": {"id": …}}, "flows": {"<key>": {"id": …, "steps": {…}}}}`. Tags and fields are keyed by name. Each entry built by the builder carries `state` (`built-off`, `failed`, or for a flow Joe has switched on, `handed-over`), `made` (`{"date", "run", "session"}`), `spec` (the plan's provenance: `{"compiler", "inputs": ["<file>@<sha-256, first 12>", …], "emailSet"}`) and `verify` (the result); the 2026-09-25 sitting's entries say `built` and carry `made` as text. An entry with no `state` is one no v1.02 run wrote: an object the builder did not make (a live segment, an email Joe made, a tag that was there before a run), never on the delete list; or, in the Project's ledger, a tag or field of the 2026-09-25 test sitting, whose `made` names it: those are on that sitting's delete list by their ZZ names, and `ledger delete` records Joe's deletion of each. A flow may map its step keys to step IDs under `steps`; nothing reads them. Edits to objects the builder did not make are kept under `edited`, by `<kind>:<id>`. `pagecmd.py refs`, `pagecmd.py reconcile` and `compile.py --ledger` read it.

**Joe's deletions (v1.01).** When Joe deletes an object by hand, its entry stays, with `"state": "deleted"`, the date and his words (`ledger delete`): `pagecmd.py refs` leaves it out, and `pagecmd.py reconcile` passes it as `deleted`, so reconcile expects it gone. A `failed` entry (a draft on the delete list) is left out of the refs too, but reconcile still expects it listed, since it exists until Joe deletes it. The compiler never names either again, by key (a tag or a field by its name) or by Encharge ID, wherever a spec, a manifest or a permission could name it, unless the same build makes that key anew. Any other entry must be in Encharge's lists: reconcile is not resolved while one is missing (a deletion not yet recorded, or a list that came back short). So the ledger must be current before the first run: step 3 ends with a reconcile.

**A rebuild takes the key (v1.01).** The compiler refuses a flow, email or segment whose key the ledger holds live: a second draft would stay beside the first. So a rebuild first takes the old entry off the key. A draft Joe agrees is superseded is marked `failed`; the rebuild's new object then takes the key, and before the run's IDs are written the old entry moves, with its state, to a key of its own, `<key>-old-<date>` (with `-2` after it for a second that day). A flow Joe has switched on is rebuilt only on his go, and is never marked `failed` while it is on (the delete list is every `failed` entry): before the compile, its entry moves, state and all, to `<key>-live-<date>` (`ledger live-move`), and it becomes `failed` only once he has switched it off after the switch-over (`ledger switched-off`, with his words). Either way the ledger keeps one entry per Encharge object (the compiler refuses a ledger holding one ID under two keys), and reconcile still expects the old one listed until Joe deletes it. A tag or a field is one per name in Encharge, so a build makes one anew only once the old one is gone (its entry `deleted`, and the account's tags or fields without it); its new entry then replaces the deleted one, which it keeps inside it under `replaced` (`ledger add` does this), before the next reconcile (reconcile does not count a tag or field the marked run made as the deleted one still there). The compiler refuses a manifest tag or field the ledger marks `failed`, or `deleted` while the account still holds it: the build would reuse it while it stayed on the delete list.

**Seeding.** The existing segments under the keys the spec format agrees: `people_in_flow` 1257090, `people_not_in_flow` 1257089, `has_any_product` 1057634, `refunded_any` 1057637, `abandoners_active_24h` 1059368, `abandoners_historic` 1057638 (the Project's ledger lacks the last: `python3 -B live/pagecmd.py ledger put ledger.json segments abandoners_historic --entry '{"id": 1057638}'`, once a spec names it). The emails are made from the master template, Encharge email VDH Master · Letter (488125, ledger key `vdh_master_letter`; D4 closed 2026-09-28), by an objects run whose manifest carries them in `shared.emails`: each names the master by its key and gives its swaps, a path and the HTML that replaces the whole value stored there (`references/api-map.md`, section 5), in the shape of spec format v0.7, section 4: the preview text and the letter, one HTML block, as proven at sittings 2a and 2b. Since v1.07 the compiler checks each email's shape (P7): exactly `key`, `name`, `subject`, `master` and `swaps`, and at least one swap, each exactly a `path` and an `html`, both text; it refuses anything else, the spec format's draft shape (`heading`, `text`, `button`, `ps`) among it, naming the email and what is wrong. (v1.06 built such an email as an unchanged copy of the master, placeholders and all, and verify passed it.) One Joe makes by hand goes in `emails` under the key the specs' SEND steps name it by, with its ID, by `python3 -B live/pagecmd.py ledger put ledger.json emails <key> --entry '{"id": <ID>, "made": "by Joe by hand, <date>"}'`; otherwise the compiler warns that the email must exist, and the run stops before its first call. `compile.py needs <manifest> --ledger ledger.json` then ends `missing from the ledger: 0 email(s), 0 segment(s)`. Every ZZ object that still exists goes in too, those Joe made by hand included, so reconcile knows them (the captures' `zz_capture`, `zz_capture_2`, `zz_capture_field` and `zz_capture_date` were deleted at sitting 1).

## Session protocol

1. **Load.** Read this file, `references/spec-format.md`, `references/api-map.md`, `references/gaps.md`, `live/RUNBOOK.md` and, before any reader check, the readers doc (section 7). Run `python3 -B scripts/check_package.py`: it must end `PASS`.
2. **Install in the page** (runbook, sections 1–2): the nine page files through `live/pagecmd.py install`, one call each, in order (`guard.js`, `runner.js`, `verify.js`, `policy.js`, `storage.js`, `transport.js`, `inspect.js`, `reconcile.js`, `sitting.js`). Since v1.10 (P20) every install call first removes `VDHSit` and records its file, and `sitting.js`'s carries the install manifest (`live/install-manifest.json`, generated by `pagecmd.py manifest`: the files, their order, a build id, each file's SHA-256 as the page holds it): the page makes `VDHSit` only if all nine came in that order, once each, and match it, so a missing, stale, reordered, altered or mixed-build file leaves no `VDHSit`, and the install's answer says why (`no VDHSit: …`; `pagecmd.py` refuses a file the manifest does not list as it is before anything is sent). Then the one-call check (nine objects, permissions 0, the guard's self-test, the fingerprint match, `VDHSit.reconcileDue()` null, since a run marker left from an earlier session is settled first, `VDHSit.unledgered()` with `durable: true` and `runs` empty (otherwise runbook 2.2 settles it, with `ledger.json` saved first: runbook 0), and `locks: true`, the browser's Web Locks). Every page file goes in one call no larger than 68,524 bytes, the size proven live at build sitting 1 (gap A21; v1.07's `sitting.js` went in at 69,611 bytes at sittings 2a and 2b): the largest, `sitting.js`, is 44,690 bytes as sent (v1.09's 56,717), the six helper files each without their whole-line comments, so what is new is only the nine-file install itself, proven once before a build uses it (runbook, section 2.6). If an install answers anything but `installed <file>: object`, or the check fails, reinstall all nine once; if it recurs, stop and tell Joe (`references/gaps.md`, A21). Save the journal and clear it (reconcile needs no journal: each run's marker records what the run made). The page must be able to keep its run marker in local storage, and must have Web Locks: a page without either starts no run.
3. **Inputs.** The ledger (above; `pagecmd.py ledger check ledger.json` must answer `ok`), the manifest and specs, `tag-groups.json`, and the session's own `permissions.json` (`[]` unless Joe has given permission in his words, each entry with the date). `python3 -B scripts/compile.py needs <manifest> --ledger ledger.json` lists what the ledger must hold before each flow runs: the emails its Send email steps name (made from the master by an objects run, or by Joe by hand) and the segments it enters. In the page, read the account's fields and tags with `VDHSit.fields()` and `VDHSit.tags()`, and save them as `fields.json` and `tags.json` with the hash check (runbook, section 3). The compiler refuses to compile without the fields. A field the manifest lists that the FlowMattic routers own (`requested_template_name` and `requested_template_url` in v50) must already be in `fields.json`: the builder never creates one (the guard refuses to), so the compiler refuses the objects plan, and any flow naming it, until Joe has made it by hand in Encharge as a Text field and the fields are read again (gap C5). Then, before the first run, `python3 -B live/pagecmd.py reconcile ledger.json --tags tags.json --fields fields.json` must answer `ok`: the ledger agrees with Encharge. If it does not, settle each difference with Joe first (an object he deleted: `python3 -B live/pagecmd.py ledger delete ledger.json <kinds> <key> --joe "<his words>"`; then write the call again).
4. **Compile.** `python3 -B scripts/compile.py objects <manifest> --ledger ledger.json --permissions permissions.json --fields fields.json --tags tags.json --tag-groups tag-groups.json -o <plan>` for fields, tags and segments, from a copy of the manifest without its emails (the runbook's checklist step 13 gives the command), and for emails, each flow's in a run of their own, from a copy holding only them (step 5); then `flow <spec>` per flow, or `group <specs>` for flows that end each other, with the same options plus `--manifest <manifest>`, so flows may use the fields and tags the objects plan creates.
   - **The Abandoners edit is left out of the objects plan, by the compiler** (v1.02): compile the objects plan from the manifest as the email set ships it. Encharge segment Abandoners (active last 24h) starts Encharge flow Abandoned Cart Email Sending Sequence, which is on, so an ordinary objects plan leaves out any edit to it, says so in its report (`leftForSwitchOver`), and uses no permission for it. Inside the switch-over, after Joe has switched that flow off (D1, step 1) and before he switches Checkout Abandon on (step 5), `compile.py objects <manifest> --switch-over …` compiles that edit alone, with Joe's permission given then. The plan's first calls read that flow, and every flow of the manifest entering Abandoners that the ledger holds and Joe has not deleted (Checkout Abandon, under its spec's key or the manifest's, and under a `-live-` or `-old-` one, failed ones too, however its trigger names the segment); the run stops there, nothing written, unless Encharge says each is switched off (`deactivated` or `deactivated-user`; any other status, or none, stops it: `failedAt: 1` or `2`, `do: 'require-off'`). The compiler refuses while the ledger holds one of them `handed-over`, and the page refuses any plan that edits Abandoners without that first read. Its run makes nothing new: step 9 records the edit with `ledger edited`. The People IN FLOW rows need Joe's permission too (D2).
   - The compiler refuses, and says why: a spec that breaks a rule, or uses a test not yet seen stored on that field type and in that place (gaps A7c, A9, A11); a tag that is not in the account, the ledger or the manifest's `shared` block (a misspelling; a product or refund tag not live yet only warns, since FlowMattic creates it at go-live); a tag, field or segment only in the manifest's `later` block ("un-park it first"), and a `TBD` value anywhere outside `later` (the text of a row it does not build aside); a permission with a wildcard, or with an action not in the table, and a spec or manifest not in the shape the spec format describes (for an email, the shape of spec format v0.7, section 4, which Seeding gives, not the old draft that v0.7 replaced: P7, since v1.07); an `onBounced` that is not on a Send email step, or that leads where `next` leads.
   - Since v1.01 it also refuses: a flow whose status is not `ship` or `gated` (`test`, or none, only for a flow whose name carries ZZ; `parked` compiles only with `--allow-parked`, for a dry run, marked `dryRunOnly`, which neither `pagecmd.py load` nor the page will take), or whose status the manifest gives otherwise (`--manifest`); a flow, step, segment or email key of anything but letters, digits, `_` and `-`, or a step key ending in `__` and a number, the form of the checks it adds when it splits a nested CHECK; a group holding one flow key or one flow name twice, and a manifest listing a field, tag, email or segment twice; a manifest field the account already holds as another type, or read-only (the account's field is used as it is, and checked again after the run); a SET FIELD on a read-only field; an object the ledger marks deleted or failed, named by key or by Encharge ID anywhere, unless the build makes that key anew (The ledger, above). A tag group's `none` inside an `any` stays one AND group of its own: a chain of checks in a CHECK, a refusal in a segment, which cannot nest (unless the group holds one tag).

Then `VDHSit.start('<name>')` and poll `VDHSit.status('<name>')` until `done`, or `error` (a start the lock refuses answers `started`, and its status then says `error`, with why), in javascript tool calls that wait 20 s or less each: one that waits longer than about 45 s times out on the tool's side while the run carries on in the page (sitting 2b: 137 calls in about 90 s). **One run at a time, in this browser:** a run holds the builder's Web Lock until it ends, so no other run, reconcile or waive starts in any tab meanwhile, however long a call hangs. Each run writes its marker in the page's local storage before its first call, with an owner token, and before each call checks that the stored marker is still its own and stores its heartbeat, with the create about to go out (`pending`); if the marker is not its own, or the storage refuses the heartbeat, it stops with nothing more sent. After each answer the marker records what Encharge made (`made`), so a reconcile knows both without the journal. A run first checks that every ID it needs is in the ledger's refs or made by an earlier call, and that none the page's refs give is one the ledger marks deleted or failed (refs older than the ledger: send `pagecmd.py refs` again), and stops with nothing sent if not; after that it stops at the first failure and reports `failedAt`, `do`, `step`, `error`, Encharge's own error text and `mayExist` (what may have been made without its ID coming back). A run that wrote and ended well is `built`: not verified yet (a run that wrote nothing leaves no marker). Its own new IDs join the page's refs, for later plans to name, only when its verify passes. If the storage refuses a marker (full or blocked), the page keeps its own copy in memory and decides on it, since it is the newer; the summary then says `markerStored: false`: verify at once if the run ended well, otherwise reconcile, and free the storage (save the journal, then clear it; if it still refuses, stop and tell Joe) before any other run, since a reload would bring back the older stored marker.
7. **Verify** with `VDHSit.verify('<name>')`, before anything could reload the page: a plain verify that passes clears the run's `built` marker, adds the run's own new IDs to the page's refs (once; never the ledger's own), and leaves a record of what the run made in the page's local storage, "verified, not in the ledger" (v1.02), until step 9; until then the page starts no other run. One that fails, plain or not, turns it `unverified`, handled as a failure (step 8). If the page's storage refuses that record, the verify does not count: the run stays `built` (a reload must lose neither), and the answer says `unledgeredStored: false`; write the ledger (step 9's `record`) at once, free the storage (save the journal, then clear it) and verify again; that verify counts, and its `next` asks for `add` again: skip it (the ledger holds the run, and `add` would refuse) and send `refs` only. A verify with an option (`ignoreName`) never counts as a pass. Every result says whether it counted (`counted`: true only for the plain verify that cleared the marker) and the run's marker after it (`markerState`), so a result is never read as a pass it was not (v1.02). A reconcile does not settle a `built` run the page still holds; after a reload it does, and says the run was never verified (`unverifiedRun`): mark what it made failed in the ledger (nothing stands in for its verify), and rebuild what is needed. For a flow: every step's type and stored editor flags, every value it holds against the configure call sent (defaults included), every link including an *On bounced* link, **no listener ids yet** (Encharge adds them when Joe switches the flow on), the notes, re-entry both ways, still off. For an objects plan: new fields against a fresh read, new tags against Encharge's answer, every segment, and every email (each key as sent, and equal to its master with the swaps made in place); after a plan that created tags, `VDHSit.tags()` must list every tag of `tags.json` and every tag it created (the tag list is not paged: a cap on it would show here). 8. **After a failure,** before anything else: permissions to `[]`, then `VDHSit.journal()` and `VDHSit.created()`, and `JSON.stringify(VDHSit.reconcileDue())` saved as `marker-<name>.json` (a reconcile that resolves clears it), then the call `python3 -B live/pagecmd.py reconcile ledger.json <the failed plan> --tags tags.json --fields fields.json` writes, sent as written: since v1.07 (P2) it carries its argument as JSON text with its SHA-256, as `pagecmd.py refs` and `load` do, and the page refuses a slip (`the argument changed on the way`) before it reads, sends or changes anything, so no hand check is needed (runbook, 2.3). Every run writes a marker in the page's local storage before its first call; a run that is cut short (a reload, a crash), fails after a write went out, or does not verify leaves it, and the page refuses any run until that reconcile has read Encharge's lists whole and found them agreeing (`ok`, `resolved`), even after a reload and a reinstall. Agreeing means: nothing the ledger knows is missing, nothing it marks deleted is still there, every object the marked run made is listed (its marker records each create Encharge answered: flows and segments by ID, tags and fields by name), every tag and field of the session's first read is listed (`--tags`, `--fields`), and nothing is in doubt. An object is in doubt when the run may have made it (the create that was out when the run stopped, or that got no answer, a timeout or a server error; or one answered without its ID) and no list shows it: a tag or a field by its name, a flow by a new flow of its name (one the ledger does not know and the marker does not name). A segment or an email the run may have made always is: the segment list is not paged (gap A19), and emails have no list call (`emailsInDoubt`). Since v1.11 (P4) reconcile also reads each email the ledger holds by its ID (`GET /v1/emails/<id>`): one the ledger holds live that is archived or gone counts as missing (`emailsMissingKnown`), one it marks deleted that is still there unarchived counts as still there (`emailsStillThere`), and one whose read fails another way leaves the lists unread (`emailsUnread`), so the marker stays. The call `pagecmd.py reconcile` writes carries the ledger's emails for this; a call without them is refused. Only Joe settles one: he looks for it by name in Encharge, the ledger records what he finds (`ledger put … --entry '{"id": <ID>, "state": "failed", …}' --joe "…"`, if it is there and he confirms it was not there before the run), and a waive clears the marker. Every object reconcile marks `madeByRun`, and every email in `madeByRun.emails` (by ID), is one the marked run made, as its marker recorded Encharge's answer: it goes into the ledger as `failed`, since that run never verified (a tag or field of the session's first read is never marked so: it was there before): `python3 -B live/pagecmd.py ledger made-ids <the failed plan> marker-<name>.json --run <name> --tags tags.json --fields fields.json --out made-<name>.json` (a plan the workspace lost is compiled again from its spec, with a fields read saved as `fields-recompile.json`, never over `fields.json`: `made-ids` reads only its names; for a marker left from an earlier session, whose first reads are gone, leave `--tags` and `--fields` out of `made-ids` and `add`, and Joe checks each tag and field of the run on the delete list before he deletes it), then, unless it wrote `{}` (nothing to add), `ledger add ledger.json made-<name>.json --run <name> --plan <the failed plan> --state failed --tags tags.json --fields fields.json`. After a reload, which loses `VDHSit.ids()`, this is how the ledger gets what the run made. Objects the ledger does not know are listed for it, and do not block. Anything missing keeps the marker: if Joe deleted it, `ledger delete` records it and the call is written again; otherwise a list may have come back short (gap A19). Reconcile lists every flow, segment, tag and field named ZZ, or with a name from the plans (`matchedBy`), known to the ledger or not. An object reconcile marks `verifiedRun` belongs to a verified run the ledger does not hold yet (the answer's `unledgered` names it): it goes into the ledger with that run (step 9), never on a delete list. An unknown ZZ object marked neither `verifiedRun` nor `madeByRun` goes into the ledger as `failed` (`ledger put … --joe`), for Joe to delete by hand; an unknown object matched by name only may be one that was there before (a tag or field says so with `atStart`), unless reconcile marks it `madeByRun`: Joe checks it before it goes anywhere near the delete list. Emails have no list call: `emailsToFind` names each email to look for (the one in doubt, and those a failed run's summary named in `mayExist`), and Joe looks for each by name. If a segment edit failed, `VDHSit.segmentsBefore('<name>', <id>)` gives the rows Joe restores (`beforeEdit`, as the segment was just before its own edit; `beforeRun`, the snapshot); after a reload, which loses both, the snapshot saved in the workspace is the record. Reconcile refuses while another copy of the builder holds the lock (a run hanging in another tab, or in an install replaced mid-run without a reload: reload that tab, on Joe's go). It also answers `ok: false`, "reconcile again in N s", for two minutes after the page stopped waiting for a call that may still be acted on: a write (not a read) that got no answer, a timeout or a server error (408, or any 5xx: a gateway's 502 to 504, Cloudflare's 520 to 524, Encharge's own 500), counted from the failure; a run cut short, counted from the first reconcile after the reload. A marker reconcile cannot resolve (a list Encharge will not give whole, an object in doubt, or a disagreement only Joe can settle) is cleared only with `await VDHSit.waiveReconcile('<run>', '<Joe's words>')`, after this page's reconcile of it came back unresolved and Joe has checked Encharge by hand.

Save any later read under another name, such as `tags-after-<name>.json`, never over `tags.json`). After a reload the record is still there, and the same file serves (`--plan` if the workspace still has it); for a run that never verified, step 8. If it is still under `unledgered`, an ID or a name went in wrong: compare the entry with `VDHSit.unledgered()`, and settle it with Joe (never `ledger supersede`: `record`, like `add`, will not write a live key twice). A plan that made nothing new (the switch-over's edit) leaves no record: its verify has no `unledgered`; skip `record`. ## What v1.02 changes (from an independent review of v1.01, 2026-09-27)

Each finding was reproduced on the shipped v1.01 package, with the reviewer's probes and with Claude's own, before it was fixed; each fix is held by a test that fails on v1.01 (`evidence/review-2026-09-27.json`). Four findings were wider than the review said: a sweep that switched off each of verify.js's 49 checks in turn found 27 whose loss no suite noticed (N1); three more wrong step values no suite saw (N2); the largest single call ever sent through the tool transport is 34 KB (then; 68,524 bytes since build sitting 1, gap A21), not the 10 KB plan it cited, and v1.01's own `sitting.js` install is 81 KB (N5); and the time-zone half of N7 is not Windows-only. In the email set's v50 export nothing compiles differently, except that the ordinary objects plan now leaves out the Abandoners edit (N3), and every plan records its provenance.

1. **N1: the verifier's checks were untested.** `tests/test_verify.js` spoils a flow, an objects plan and an email on the mock one way at a time, and requires the one check that should see it: every check of `verify.js` now has a case that fails when that check is lost (flow status, step count, notes and the rest).
2. **N2: step values were checked only against the plan's own expectations.** `tests/test_flows.py` compiles every ship and gated v50 flow, the group, the objects and switch-over plans, the live tests' specs and hand-made specs for every step type, and checks each call against the spec by the spec format's and the API map's rules, written out on their own: values, editor flags, links and their data, the checks' wiring, notes, re-entry, the read-back, the canvas rows, and that the plan's `expect` is what the calls send.
3. **N3: the Abandoners edit was kept out by a hand-made manifest copy.** The compiler leaves it out of an ordinary objects plan (named by key or ID, however the ID is written, whatever permissions are given), and `--switch-over` compiles it alone, behind first calls that stop the run, nothing written, unless Encharge flow Abandoned Cart Email Sending Sequence, and Encharge flow Checkout Abandon once the ledger holds it, are each switched off.
4. **N4: a permission's provenance was not checked.** The compiler refuses an entry without Joe's words or the date, or whose words are a bracketed note or a test's, and any permission file in the package's `tests` folder, unless `--offline-permissions`, which marks the plan `offlineOnly`; `pagecmd.py` and the page never load such a plan. The page sets a run's permissions itself from the plan it loaded by its hash, and refuses a plan whose permissions lack words or a date.
5. **N5: the largest plans had never been through the tool transport.** `pagecmd.py load` splits a plan whose command would pass 24,000 bytes into parts, each under the 34 KB proven live (then; 68,524 bytes since build sitting 1), each a JSON string of its own; `VDHSit.loadPart` keeps them until all have come, in any order, and loads the whole by its hash. `pagecmd.py sizes` gives each plan's size and parts. The install of `sitting.js` (68 KB in v1.02, its whole-line comments left out) stays the largest single call: a stop rule and gap A21.
6. **N6: a verified run's record was lost to a reload before the ledger was written.** A passing plain verify leaves "verified, not in the ledger" in the page's local storage, with the run's IDs, its plan's hash and provenance; no run starts until the ledger holds it, which the page sees when `pagecmd.py refs` sends what the ledger holds, by kind. After a reload, `VDHSit.unledgered()` gives what the run made, and reconcile lists its objects (`verifiedRun`) whatever their names.
7. **N7: the suites failed on Windows.** The compiler and `pagecmd.py` write UTF-8 with LF line endings on stdout and stderr, whatever the console's code page, and the compiler prints a key as written (a newline as `\n`); `check_package.py` first checks Python has time-zone data for Europe/Paris, and names the fix (`pip install tzdata`).
8. **N8: a verify with an option read ok while the run stayed unverified.** Every result says whether it counted and the run's marker after it; one with an option says it never counts. No re-verify: a verify problem still means a rebuild (the design is kept).
9. **N9: a plan recorded nothing about its inputs.** Every plan carries `provenance`: the compiler's version and hash, and the SHA-256 of the catalogue and every input file; no clock, so the same inputs still give the same plan byte for byte. The run marker and the ledger record carry it.
10. **N10: the ledger was edited by hand.** `pagecmd.py ledger` (`SKILL.md`, The ledger), tested by `live/test_ledger.py`.

**The reviews of the fixes** (each round by fresh independent reviewers, one of the code and one of the documents, running every claim against the code; `evidence/review-2026-09-27.json`, `reviewsOfFixes`). No round found a blocker. What they found, and v1.02 now does:
- The switch-over's first call stopped only on the exact status `"on"`: it now goes on only on `deactivated` or `deactivated-user`, and reads Encharge flow Checkout Abandon too once the ledger holds it (D1's second condition). A ledger entry holding Abandoners' ID as text slipped past the gate: every flow, segment and email ID in a ledger must be a whole number, and an ID written as text is still recognised.

The ledger's IDs go to the page by kind (an email's ID no longer stands for a flow's); a tag or field left out as there before is held, so its run's record clears.

The permission words are judged alike by the compiler and the page (a test's words, invisible characters, a date no calendar has).
- The documents said 81 KB for the `sitting.js` install, and still required hand edits of the ledger: corrected, and each step has its command and the answer it gives.
- The v50 manifest lists two fields the FlowMattic routers own, `requested_template_name` and `requested_template_url`, which the guard never lets the builder create: the first objects run would have stopped at the first of them, after six fields were made. - A failed run's first-read tags could reach the delete list through `made-ids`, and a later read saved over `tags.json` could keep a run's own tags off it: `made-ids` takes the first reads, and the tools refuse a read saved after what it judges. A failed tag's name is held for the page (its run's record clears); `keep` records a failed tag or field Joe keeps; `put` needs Joe's words for the delete list, and never fails a live object the builder did not make; `switched-off` takes only a key `live-move` made; the ledger commands refuse unknown options and impossible dates; `edited` keeps the snapshot's rows, and is used after the objects plan's People IN FLOW edit too.

- The `sitting.js` install was about 100 KB, three times the largest call proven: it now goes without its whole-line comments, 68 KB, the code the suites run unchanged (A21). The page files hold no backslash-p or backslash-b escape, which the transport was never probed with.
- The test-word check let plurals and glued words through: the labels are now found in the words' letters and digits alone. The switch-over reads Checkout Abandon by its spec's key as well as the manifest's, and a failed one too. `made-ids`'s answer carries the run's start, so `add` refuses a later read on that path too. No command can give a live object the builder did not make a state but `deleted`. A tag or field Joe kept is never made again. Reconcile names any flow on the delete list that Encharge does not list as switched off (`failedOn`).
- The comment-free install refuses any line it cannot cut safely (code beside a one-line comment, a line carried on by a backslash), and the rehearsal runs the text the page holds, not the file. A record carries when its run started, and a waive's answer too, so a first read saved after that is refused on every path. `failedOn` counts any status but the two of a flow switched off. A second `add` of the same run is told to send `refs`.
- Test gaps: a case now fails for each check or fix a reviewer's mutation left unseen (the edited segment's read-back, End Flow by ID, the notes' places, the parts of a plan, the ledger's writes, the line endings under a Windows code page, the switch-over's alias, `-live-` and key reads, the foreign value's memory, each word of the list, the date bounds).
